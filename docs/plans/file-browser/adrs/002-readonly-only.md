# ADR-002: MVP 严格只读

## 状态

已采纳(2026-05-20)

## 上下文

文件浏览功能可以扩展到:编辑、新建、删除、重命名、上传、下载、视频/音频、归档浏览、git 集成……ROADMAP 已把"SFTP/SCP 文件管理"列为不做(产品定位偏离)。要为本次实施划定边界。

## 决策

**MVP 严格只读**:仅支持 listdir / readfile / 预览(文本 + 图片)/ 搜索。所有写操作、上传、下载二进制、视频/音频预览、归档内部浏览、git 集成全部不做。

## 拒绝的替代方案

### 方案 A:做最小写(只允许文本文件保存)

- 写操作引入并发安全(谁覆盖谁)、跨设备 rename、权限/SELinux 困难;
- 安全模型从"读 = 信息泄露"变成"写 = 任意命令执行可能"(写 shell rc / cron / systemd 直接被持久化);
- 与"远程 PTY 控制"定位明显冲突——用户要写文件本来就能在终端里 `vim` / `cat >`。

### 方案 B:支持下载

- 安全风险高(token 一旦泄露,远程取代码、密钥);
- 与"只读浏览"边界模糊,容易功能蔓延到"网盘"。

## 理由

1. 控制实施风险:第一版聚焦"看",安全边界一目了然;
2. 与 ROADMAP "不做完整文件管理"对齐;
3. 真正的写/编辑工作流仍走终端(vim/code/edit),这是项目主战场;
4. 后续如确有强需求,可基于本次架构平稳加层(写操作必须额外过一层"写白名单",见 future work)。

## 后果

- ✅ 安全模型简单清晰:只信任 `checkWorkdir` 边界,无写竞态;
- ✅ 实施工作量缩到 ~5.6d;
- ⚠️ 用户若期望"在网页上改文件保存",会失望——i18n 文案与 README 需明示;
- ⚠️ 未来加写功能时,必须把"写许可"作为单独的策略字段(`workdirWriteAllow`),不与 `workdirAllow` 复用语义。
