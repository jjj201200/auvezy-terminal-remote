## 引言

Auvezy Terminal Remote 是一个面向移动端 / 桌面端 Web 浏览器的远程终端，主要使用场景是在 Claude Code 这类现代 TUI 程序里替代物理终端。Web 浏览器原生没有终端的"鼠标 / 键盘 / 触摸"语义，xterm.js 又是一个为桌面键盘 + 鼠标设计的库——把它放进 iOS Safari、Android Chrome 这种触摸优先的环境里，会出现一连串错配：

- xterm.js 把触摸事件 short-circuit 掉（mouse reporting active 时直接 `return`），TUI 程序收不到 click
- xterm 内部 mousedown handler 无条件 `this.focus()` helper-textarea，iOS 上立即弹起 IME 但用户根本没想输入
- 触摸滑动 = 翻页 vs. 滚一行 vs. 选择文本 三个意图无法靠手势单独区分
- TUI 程序自己启用 mouse reporting 就把"点击 = 选择"的桌面默认语义吞掉，用户失去了拖选能力
- iOS Safari 一旦 `.focus()` 不在 user gesture 同步链路里，软键盘根本不弹

本项目花了相当篇幅在前端做"输入接管层"——拦截 / 重写 / 转发原始输入事件，把它们规范化成一组明确的、可设置、可关闭、平台一致的交互。本报告把这层接管的所有细节、设计取舍、冲突解决逻辑、跨平台差异完整记录下来。

## 第一章 协议背景：为什么用 SGR 1006

### 1.1 章节引言

理解后续所有设计的关键前提：**TUI 程序怎么"看到"鼠标点击 / 滚轮 / 拖动**。Web 浏览器里没有真正意义上的"硬件鼠标信号"传给 TUI，必须经过一层 ANSI 协议转换。这一章讲清楚这个协议，后面的所有"接管"行为本质上都是**在前端伪造这个协议的字节**。

### 1.2 xterm 鼠标协议演进

xterm 终端从 1990s 起就定义了把鼠标事件**编码成 ANSI escape sequence 发给 PTY** 的协议。TUI 程序读 PTY 字节流时识别这些序列，做出"我被点击了 / 滚动了"的反应。协议有几代演进：

| 协议 | DECSET 编号 | 触发什么事件 |
|---|---|---|
| X10 兼容 | `?9` | 仅鼠标按下 |
| X11 normal | `?1000` | 按下 + 抬起 |
| Button-event tracking | `?1002` | + 按下时拖动 |
| Any-event tracking | `?1003` | + 任意鼠标移动 |

事件**编码方式**也分几代：

| 编码 | DECSET | 编码格式 | 坐标上限 |
|---|---|---|---|
| X10 默认 | `?9` 自带 | 3 字节，`+32` 偏移 | 223×223 |
| UTF-8 | `?1005` | UTF-8 多字节 | 2015×2015 |
| **SGR** | `?1006` | 纯 ASCII 数字 | 无上限 |
| URXVT | `?1015` | rxvt 自家方案 | — |

### 1.3 SGR 1006 字节格式

本项目**全程**使用 SGR 1006 编码，因为它纯文本、可读、坐标无限制。格式：

```
CSI < button ; col ; row M       ← 按下事件，结尾大写 M
CSI < button ; col ; row m       ← 抬起事件，结尾小写 m
```

`CSI` 即 `\x1b[`。`button` 取值（仅列项目用到的）：

| button 值 | 含义 |
|---|---|
| 0 | 左键 |
| 1 | 中键 |
| 2 | 右键 |
| 64 | 滚轮上滚（看历史） |
| 65 | 滚轮下滚（看下面） |

例：左键点击屏幕 col=42, row=15 = `\x1b[<0;42;15M\x1b[<0;42;15m`（一对 press+release）。
滚轮上滚一格 = `\x1b[<64;42;15M`（仅 press，无 release）。

`col` / `row` **从 1 起编号**（不是 0），无效坐标 TUI 可能崩，本项目用 `Math.max(1, ...)` 兜底。

### 1.4 Claude Code 启用的 mode

Claude Code TUI（基于 ratatui）启动后立即发：

```
\x1b[?1000h\x1b[?1002h\x1b[?1003h\x1b[?1006h
```

启用了所有事件类型（按下 / 抬起 / 拖动 / 任意移动）+ SGR 编码。退出时发对应的 `l` 序列关闭。

vim 的 `set mouse=a`、htop、btop、tmux 等 TUI 也启用类似组合。**本项目的所有 mouse-related 接管，都以 mouse reporting 是否激活为前提**——不激活就原样让 xterm 处理（普通 shell 用户期望的"鼠标选文本复制"行为）。

### 1.5 为什么不用 xterm 内置转换

xterm.js v5.5.0 内部本来就有 mouse → SGR 的转换路径（`Terminal.ts:606-690` 的 `sendEvent` 函数 + `CoreMouseService.consumeWheelEvent`），按理不需要我们自己拼字节。但**项目里几乎全部场景都绕过了 xterm 的内置转换**，原因（按发现顺序）：

1. **xterm 在 mouse-active 时把触摸事件 early-return**（`Terminal.ts:835-846`）：移动端触摸不会被转 SGR，等于完全不响应
2. **xterm v5 没监听 `touchend`**：连 tap → 合成 click 的 fallback 链都不完整
3. **xterm 内部 wheel 转换有 cellHeight / dpr 校验**：renderer 异常时直接返回 0
4. **xterm v5 mousedown handler 无条件 `this.focus()`**：iOS 上立即弹 IME，无法绕开
5. **`getMouseReportCoords` 访问 `_renderService.dimensions` 在 renderer dispose 后崩溃**：触发 `Cannot read properties of undefined (reading 'dimensions')` 异常

所以本项目选择了"完全自己拼字节"的路线，xterm 只用作渲染器 + 字节缓冲。xterm.js 7.0 master 的 PR #5685 已经修了触摸路径，但仅覆盖滚动不覆盖点击；且未发布。

### 1.6 小结

SGR 1006 是本项目所有"鼠标动作"的真正语义层。前端拦截所有触摸 / 鼠标事件，根据用户意图（设置项 + 手势识别）决定是否拼对应字节发往 PTY。本章是后面所有章节的协议前提。

## 第二章 设置项与数据模型

### 2.1 章节引言

所有交互行为都受**用户配置**约束。配置数据从 `~/.auvezy/terminal-remote/config.json` 落盘，经 `ensureDefaultUserConfig` normalize 后通过 `/api/config` 推送到前端。本章列出与交互直接相关的所有字段、默认值、运行时含义。

### 2.2 InputPrefs 完整字段

定义在 `shared/src/defaults.ts` 的 `InputPrefs` interface：

| 字段 | 类型 | 默认值 | 含义 |
|---|---|---|---|
| `useInputBar` | `boolean` | `true` | 输入方式：`true` = 底部 InputBar 行编辑后回车一次性发；`false` = DirectInputCapture 实时按键转发 |
| `tuiScrollEnabled` | `boolean` | `true` | TUI 滚动接管总开关：`false` 时 hook 不挂任何 listener，输入完全由 xterm 自带处理 |
| `tuiTapEnabled` | `boolean` | `true` | 移动端触摸 tap → SGR 点击：`false` 时 tap 不发 SGR（仍可点击 toolbar 等 React 元素，只是不传给 TUI） |
| `scrollLines` | `number \| 'half' \| 'full'` | `3` | 一次"滚动事件"对应的行数：数字 1/3/5/10、`'half'`= floor(rows/2)、`'full'`= rows |

字段的命名空间放在 `input` 子节点下（`UserConfig.input.*`），与显示偏好 `display`、网络偏好 `network` 平级。

### 2.3 默认值取值理由

每个默认值的选择背后都有具体场景考量：

- **`useInputBar: true`**：覆盖最广泛的"中文 IME + 长命令"场景。直接输入模式在移动端 IME 兼容性差（已知 iOS WebKit 上 xterm helper-textarea 的 input 事件不可靠），不适合做默认。
- **`tuiScrollEnabled: true`**：用户使用 ATR 的核心场景就是在 Claude TUI 里看 transcript；普通 shell 不在 alt-screen 时 hook 自动不接管，对老使用习惯无影响。
- **`tuiTapEnabled: true`**：移动端用户在 Claude TUI 内点按钮是基本需求，关闭后整个移动端 UX 半残。
- **`scrollLines: 3`**：与 `CLAUDE_CODE_SCROLL_SPEED` 的常见默认值接近，体感与桌面浏览器原生 wheel 一格滚 3 行接近。

### 2.4 normalize 与字段保活

`ensureDefaultUserConfig`（`shared/src/defaults.ts:505+`）在每次读取 / 写入配置前都会跑一次 normalize：

- 类型不对（如 string 误传到 boolean 字段）→ 回退到 default
- 缺失字段 → 显式补上 default

**关键约束**：每加一个新字段，必须在三处都改：
1. `InputPrefs` interface 加字段
2. `DEFAULT_INPUT` 加默认值
3. `ensureDefaultUserConfig` 内的 input 子块 normalize 加这个字段的提取

漏了第 3 步会导致**字段被 strip**——前端 PUT 进来的值在下一次 GET 时丢失，"保存了但读不到"。这条已经写入项目 CLAUDE.md 与本作者的 long-term memory。

### 2.5 设置面板 UI

设置面板（`SettingsModal.tsx`）的 tab 结构：

| Tab | 内容 |
|---|---|
| 通用 | 仅语言切换 |
| **操作** | ControlsSection（输入方式 / TUI 滚动 / 触摸点击 / 滚动行数）+ 快捷键 + 命令 |
| 显示 | 调色板 / 列数 / 字间距 |
| 网络 | 重连策略 |
| 开发 | Eruda / Bridge 等开发者工具 |
| 关于 | 版本、链接 |

ControlsSection 内部按钮组渲染（不用 Toggle，避免与 LanguageSwitch 风格不一致），顺序固定：

1. 输入方式（底部输入框 / 直接输入）
2. TUI 滚动接管（开启 / 关闭）
3. TUI 触摸点击（开启 / 关闭）
4. 每次滚动行数（1 行 / 3 行 / 5 行 / 10 行 / 半屏 / 一屏，TUI 滚动关闭时整组禁用 + 灰显）

`useInputBar` 的两个值在 i18n 里叫"底部输入框 / 直接输入"，不是 "true / false"——任何二选一开关都用具名按钮，避免出现"true 是开还是关"的歧义。

### 2.6 小结

配置体系简单但严格：4 个字段 + 默认值都打开 + normalize 必经 3 处同步。后续章节的所有行为分支都参照这 4 个字段判定。

## 第三章 输入方式：InputBar vs DirectInputCapture

### 3.1 章节引言

终端输入有两种根本不同的模型：**行编辑后回车一次性发**（典型 PowerShell / cmd.exe 行为）vs **每个按键实时发**（典型 SSH / vim / Claude Code 行为）。两者在中文 IME、键盘隐藏 / 显示、多字符粘贴等场景下表现差异极大。本项目两种都支持，由 `useInputBar` 设置切换。

### 3.2 InputBar 模式（默认）

**适用场景**：移动端中文输入、长命令、需要复制粘贴一段文本。

**行为模型**：
- 屏幕底部固定一个 `<form>` 容器，包含一个真实的 `<textarea>` + 发送按钮
- 用户输入文字 → 文字保留在 textarea 内 → 看到自己打的字 → IME 候选词正常工作
- 用户按 Enter（移动端虚拟键盘的发送键）/ 点击发送按钮 → 整段文本一次性 `send({type:'user_input', data: text + '\r'})` 发到 PTY
- 输入框非受控（uncontrolled），通过 `useImperativeHandle` 暴露 `focus / setValue / clear` 三个 API 给外部

**关键技术细节**：
- textarea 对外不可见（视觉上被设为透明 / 占位），用户看到的是自定义渲染的 `<.display>` 区域 + `<.caret>` 自管光标
- 这种 "DOM-as-truth + 自渲染" 模式仿照 CodeMirror 6 的设计，目的是规避 iOS QuickType / 智能标点对 textarea 内容的污染（详见 `useTextareaInputGuard.ts`）
- 拼音 IME 输入期间通过 `composing` 状态冻结，不发送候选词到 PTY；`compositionend` 时一次性整段发
- 智能标点检测（如 `cd .` 被 iOS 改成 `cd ..` 这种意外修改）通过 LCP 比较 + smart-punct 模式识别，回滚浏览器的破坏

### 3.3 DirectInputCapture 模式

**适用场景**：桌面端、需要每个按键实时反馈（vim 模式切换、Ctrl-C 中断等）。

**行为模型**：
- 在 xterm 容器内挂一个 1px × 100% 宽的透明 `<textarea>`，bottom: 0 贴底
- 它接管全部键盘 / IME 输入：用户按 `a` → input event → `sendDirect("a")` → 立即发往 PTY
- 没有"积攒后回车"的概念，每个 keystroke 都是独立 PTY input
- xterm 的 helper-textarea 通过 CSS 不被点击命中（pointer-events:none 在 useInputBar=true 时挂；false 时不挂，需要 hook 介入抢焦点）

**关键技术细节**：
- 设计动机：xterm 5 的 helper-textarea 在 iOS WebKit 上的 input event 不可靠（仅 backspace 的 keydown 工作），用我们自己挂的 textarea 绕开
- 挂在 bottom 是为了 IME 弹起后该行始终在可视区底部，焦点不会被 visualViewport scrollIntoView 扯走
- font-size: 16px 防止 iOS 自动缩放页面
- caret-color: transparent / opacity: 0 视觉隐藏
- compositionstart / compositionend 期间冻结，end 时把 e.data 整段 send

### 3.4 模式切换的副作用

切换 `useInputBar` 字段后立即生效（不需要刷新），但有几个隐藏行为：

- **InputBar / DirectInputCapture 都用 `useInputBar` 控制条件渲染**：切换时 React 卸载一个挂另一个，焦点丢失
- **xterm `setOnData(null)`**：项目里固定置 null，xterm 自带的 onData 路径不接外部转发；输入完全走我们自己的两个 textarea
- **PC 端 click 时**：useInputBar=true 模式 + mouse-active 时不 focus（避免移动端 click 弹 IME，PC 上虽然不弹但行为对齐）；useInputBar=false 模式总是 focus DirectInputCapture（PC 需要它接键盘）

### 3.5 小结

输入方式是个二选一的根本模型，移动端默认 InputBar 兼顾 IME 友好，桌面端可切到 Direct 模式获得"按键实时"体验。两种模式的 textarea 都不是 xterm 自带的，都是项目自挂的，xterm 仅做渲染。

## 第四章 TUI 滚动接管

### 4.1 章节引言

桌面浏览器有原生鼠标滚轮事件，xterm.js 默认会处理它做 scrollback 滚动。但**在 TUI 内部**用户期望的不是"翻看 xterm 缓冲区"而是"让 TUI 程序自己滚动它的 transcript"——Claude 的对话历史、vim 的 buffer、less 的 pager 都需要 TUI 程序内部响应滚动。移动端更彻底，连 wheel 事件都没有，只有触摸滑动。本项目的 TUI 滚动接管把两边都统一到"发 SGR mouse byte 给 TUI 程序"。

### 4.2 总开关与上下文

**开关条件**：`tuiScrollEnabled !== false`（默认 true）→ hook 接管；`false` → effect 直接 return，所有 wheel / touch 都给 xterm 自己。

**生效条件**（即使总开关开着，也要满足）：
1. 当前在 alt-screen（`isAltScreen(term)` 检查 `term.buffer.active.type === 'alternate'`）
2. mouse reporting 激活（`isMouseReportingActive(term)` 读 `term._core.coreMouseService.areMouseEventsActive`）
3. 容器 element 已挂载

任一条件不满足 → `getCtx()` 返回 null → wheel / touch 不接管，让 xterm 走原生 scrollback / 系统选择行为。

### 4.3 桌面 wheel 路径

桌面用户滚一格鼠标轮：

1. capture 阶段拦截 `wheel` 事件
2. 检查 `getCtx()`，不通过则放过
3. `e.stopPropagation() + e.preventDefault()`：阻止 xterm 自己处理 + 阻止页面 scroll
4. 解析 `scrollLines` 配置 → `linesPerNotch`
5. `e.deltaY > 0` → button code 65（向下）；否则 64（向上）
6. 把 `e.clientX / clientY` 通过 `clientToCell` 换算为 cell col/row（鼠标位置精确）
7. 拼 `linesPerNotch` 个 SGR wheel 字节连成一段 payload
8. `onSendKey(payload)` → backend → PTY → TUI 收到 N 次 wheel button → 滚 N 行

例：`scrollLines=3`，用户滚轮一格向上 → 发 `\x1b[<64;col;rowM\x1b[<64;col;rowM\x1b[<64;col;rowM` → TUI 滚 3 行历史。

### 4.4 移动端触摸滑动路径

触摸没有"一格 wheel notch"概念，需要按距离换算。

**步骤分解**：

1. `touchstart`：记录起点 (startX, startY)、`pendingDelta = 0`、`active = true`、`vertical = false`
2. `touchmove`：
   - 如果还没判方向：等 ady ≥ 12px 或 adx ≥ 12px
   - 比较 ady > adx × 1.5 → 是垂直 swipe，接管；否则 `active = false`，放给 xterm / 系统做横向选择
   - 接管后每帧累加 `pendingDelta += deltaThisMove`
   - rAF 合批，避免每个 touchmove 都发字节
3. `flushSwipe`（rAF 回调）：
   - `baseSteps = trunc(pendingDelta / SWIPE_STEP_PX)`，`SWIPE_STEP_PX = 80`
   - 一个 step = 一次"滚动事件"= `linesPerStep` 行
   - `totalLines = baseSteps × linesPerStep`
   - button = totalLines > 0 ? 64 : 65（手指下滑 baseSteps>0 = 看上面 = 上滚）
   - 发 |totalLines| 个 SGR wheel byte
4. `touchend`：清状态

**STEP_PX = 80px** 是经验值：iPhone 上一根手指轻松一推约 80px，太小会因为微抖动误触，太大会让翻页变重。

**坐标取屏幕中心**（`Math.floor(cols/2), Math.floor(rows/2)`）：触摸 swipe 不在乎精确坐标，TUI 一般也不读 wheel 字节的坐标做特殊处理。

### 4.5 scrollLines 设置项与运行时解析

`scrollLines` 配置可能是数字或字符串：

```ts
function resolveLines(rows: number): number {
  const v = scrollLinesRef.current;
  if (v === 'half') return Math.max(1, Math.floor(rows / 2));
  if (v === 'full') return Math.max(1, rows);
  return Math.max(1, Math.trunc(v));
}
```

`'half'` / `'full'` 在每次发 SGR 时**实时**用当前 `term.rows` 计算，所以窗口尺寸变化（旋屏 / 缩放）后下一次滚动自动跟随新尺寸——用户体感是"半屏"始终是"当前可见区一半"。

### 4.6 设计取舍：为什么用 SGR wheel 而非 PgUp/PgDn

早期版本（v0.4.x 中段）用过 `\x1b[5~` (PgUp) / `\x1b[6~` (PgDn)：

- **优点**：所有 alt-screen TUI 都响应 PgUp/PgDn（vim、less、htop、Claude）
- **缺点**：粒度只能"翻页"——一次跳半屏左右，用户没法"滚 3 行"那种细颗粒控制

切换到 SGR wheel 之后：

- **优点**：逐行精确控制（TUI 一格 wheel byte = 滚一行），`scrollLines` 设置真正生效
- **缺点**：要求 TUI 启用 mouse reporting（普通 shell 不开就不能滚 transcript，但普通 shell 也没 transcript 概念，xterm 自带的 scrollback 接管了，无影响）

最终保留 `tuiScrollEnabled` 总开关给少数偏好"我就要 xterm 默认行为"的用户。

### 4.7 小结

TUI 滚动接管把"鼠标轮一格"和"触摸滑 STEP_PX"统一映射为"发 N 行 SGR wheel byte"，N 由用户设置 `scrollLines` 决定。两个端用一套 `scrollLines` 配置，体感一致。

## 第五章 TUI 触摸点击与桌面鼠标点击

### 5.1 章节引言

让 TUI 程序知道"用户点了某个按钮"在桌面上是 xterm 自带功能，但移动端因为 xterm 不处理触摸 + iOS 浏览器特殊行为，必须重写。这一章把 PC mouse + 移动 touch 的点击路径都讲清楚，包括它们各自的"焦点副作用"如何处理。

### 5.2 移动端触摸 tap 路径

**判定条件**（在 `touchend` 时同步算）：

| 条件 | 含义 |
|---|---|
| `tuiTapEnabledRef.current` | 设置项 `tuiTapEnabled !== false` |
| `tapStartTs > 0` | touchstart 当时记下了时间戳，没被清掉 |
| `!movedBeyondTap` | 手指位移没超过 10px |
| `!longPressFired` | 没触发长按（长按走 IME 路径，不发 SGR） |
| `elapsed < 500ms` | 总时长不超过 500ms |

全部满足 → 是 tap → 发 SGR 点击。

**附加分支：IME 收起优先**

```ts
const focused = document.activeElement as HTMLElement | null;
const isTextInputFocused =
  focused?.tagName === 'TEXTAREA' || focused?.tagName === 'INPUT';
if (isTextInputFocused) {
  userIntentBlurTs = performance.now();
  focused?.blur();
} else {
  // 发 SGR
}
```

如果当前焦点在 textarea / input（说明 IME 是开着的），tap 改成 blur 收起 IME，**不发 SGR**——避免"点屏想关键盘却误触发了 TUI"。`userIntentBlurTs` 标志会让后面的 focus guard 尊重这个主动 blur。

**SGR 发送**：

```ts
const { col, row } = clientToCell(elt, term, ct.clientX, ct.clientY);
sendClick(0, col, row); // button 0 = 左键
lastTapSgrTs = performance.now();
```

`lastTapSgrTs` 记下时间戳，给后续合成 mousedown 用作抑制窗口（避免双发）。

### 5.3 桌面 mousedown 路径

PC 鼠标按下与移动端有完全不同的处理需求：

**问题**：xterm v5 mousedown handler（`Terminal.ts:773`）会调 `getMouseReportCoords` 访问 `_renderService.dimensions`。renderer 因 WebGL context 丢失或其他原因 dispose 后，`dimensions` 是 undefined，抛 `Cannot read properties of undefined (reading 'dimensions')`。这个崩溃在 PC 上时不时复现，导致单击完全失效。

**解决**：hook 自己接管 mousedown，绕开崩溃路径，自己拼 SGR：

```ts
const onMouseDown = (e: MouseEvent): void => {
  const ctx = getCtx();
  if (!ctx) return;
  e.stopImmediatePropagation();
  e.preventDefault();
  const fromTouch = performance.now() - lastTouchTs < TOUCH_MEMORY_MS;
  const inSuppressWindow = performance.now() - lastTapSgrTs < TAP_SUPPRESS_MS;

  // 触摸合成 + tap 抑制窗口：不重复发
  if (fromTouch && inSuppressWindow) return;

  const button: SgrButton = e.button === 1 ? 1 : e.button === 2 ? 2 : 0;
  const { col, row } = clientToCell(ctx.elt, ctx.term, e.clientX, e.clientY);
  sendClick(button, col, row);

  // PC 真鼠标：手动喂 SelectionService 启动文本选择
  if (!fromTouch) {
    dispatchSelectionMouseDown(ctx.term, e);
  }
};
```

**关键三点**：

1. **`stopImmediatePropagation` 阻止 xterm 主 mousedown handler** — 既绕开崩溃，又阻止 xterm 自己 focus helper-textarea（避免 iOS 弹 IME 副作用）
2. **抑制窗口** — 移动端 tap 已经在 touchend 发了一次 SGR；浏览器后续合成的 mousedown 在 300ms 内不重复发
3. **`dispatchSelectionMouseDown`** — 仅 PC：手动把 mousedown 转给 xterm 的 SelectionService，启动拖选（详见第七章）

### 5.4 触摸来源识别

PC 鼠标和"触摸合成的 mousedown"在 MouseEvent 上无法直接区分（`MouseEvent.pointerType` 在某些浏览器是空的）。本项目用**时间戳标志**：

```ts
const TOUCH_MEMORY_MS = 800;
let lastTouchTs = 0;
// touchstart 时设：
lastTouchTs = performance.now();
// mouse 事件里判：
const fromTouch = performance.now() - lastTouchTs < TOUCH_MEMORY_MS;
```

理由：浏览器在 touchend 后通常 100-300ms 内派发合成 mousedown / mouseup / click。800ms 窗口足够覆盖最慢的合成事件（iOS Safari 双击延迟可能拖到 ~300ms），同时不至于把"触摸 → 一秒后真鼠标点击"误判为触摸。

### 5.5 click 拦截

仅触摸合成的 click 拦下：

```ts
const onClick = (e: MouseEvent): void => {
  if (!getCtx()) return;
  const fromTouch = performance.now() - lastTouchTs < TOUCH_MEMORY_MS;
  if (!fromTouch) return;
  e.stopImmediatePropagation();
  e.preventDefault();
};
```

**理由**：浏览器在 tap 后合成 click 的默认行为之一是"把焦点转移到 click target"。如果不拦，长按 armed 后刚 focus 的 InputBar 会在合成 click 到达时被抢回 body。PC click 不拦——它要冒泡到 InstanceView 容器的 onClick 触发 focus 转移。

### 5.6 InstanceView 容器 onClick

容器自己也挂 onClick（在 `terminalWrap` 上）：

```tsx
onClick={(e) => {
  // 文本选区场景跳过：让用户能选择 / 复制
  const sel = window.getSelection();
  if (sel && sel.toString().length > 0) return;
  if (!(e.target as HTMLElement | null)?.closest?.('.xterm')) return;
  // mouse-active + InputBar 模式：不 focus，避免 click 弹 IME（长按才弹）
  if (isMouseReportingActive(termRef.current) && useInputBar) return;
  if (useInputBar) {
    inputBarRef.current?.focus({ preventScroll: true });
  } else {
    directCaptureRef.current?.focus({ preventScroll: true });
  }
}}
```

**四个分支**：

| mouse-active | useInputBar | 行为 |
|---|---|---|
| false（普通 shell）| true | focus InputBar → IME 弹 |
| false（普通 shell）| false | focus DirectInputCapture |
| true（TUI）| true | 不 focus（避免 click 弹 IME，长按才弹）|
| true（TUI）| false | focus DirectInputCapture（PC 需要它接键盘）|

注：移动端到达这个 onClick 的前提是 hook 没拦下 click——但我们已经在 hook 里 fromTouch=true 时拦了。所以这里实质处理的是 PC click + 极少数 hook 没接管的场景。

### 5.7 小结

点击路径在 PC 和移动端走完全不同的代码：移动端是 touchend 同步识别 tap → 发 SGR；PC 是 mousedown capture 拦截 → 发 SGR + 喂 SelectionService。两边汇总到同一个 `sendClick` 函数发字节，但**周边的焦点逻辑、抑制窗口、IME 收起、双发防护**完全独立设计。

## 第六章 IME 唤起与收起

### 6.1 章节引言

iOS Safari 的软键盘（IME）只在 `<textarea>` / `<input>` 获得焦点时弹起。本项目最棘手的设计就是：**怎么在合适的时候 focus 让 IME 弹，又在合适的时候 blur 让 IME 收**——同时不能让"用户想点 TUI 按钮"误触发 IME。

### 6.2 user gesture 同步链路约束

iOS Safari **硬性要求**：`.focus()` 调用必须在 user gesture 同步链路内才能让软键盘弹起。也就是说：

- `touchstart` / `touchend` / `click` 等事件 handler **同步**调 `.focus()` ✓ 弹起
- `setTimeout(() => .focus(), 0)` ✗ 不弹
- `await fetch(...).then(() => .focus())` ✗ 不弹
- `requestAnimationFrame(() => .focus())` ✗ 不弹

这条规则导致**长按定时触发 IME 弹起**这件事根本不可能在 setTimeout(600ms) 回调里直接做。

### 6.3 长按触发 IME 的实现

**策略**：长按计时器只标记"长按已 armed"，**真正调 `.focus()` 留到 touchend 同步链路**：

```ts
// touchstart 启动计时
longPressTimer = window.setTimeout(() => {
  longPressTimer = 0;
  if (movedBeyondTap || tapStartTs === 0 || !getCtx()) return;
  longPressFired = true;          // ← 仅标记
  cancelProgress();                // 关进度条 UI
  // 不调 onLongPress，等 touchend
}, longPressMsRef.current);

// touchend 同步触发
if (longPressFired) {
  onLongPressRef.current?.();      // ← 调 inputBarRef.focus()
  // ...启动 focus guard（见 6.5）
}
```

**用户体感**：
- 按住 600ms 进度条满 → 进度条消失（armed 信号）
- 抬起手指 → IME 弹起

唯一妥协：用户必须**抬手才能弹 IME**，不是按到 600ms 自动弹起。但这种语义反而更清晰（"我要输入 → 我抬手"）。

### 6.4 短 tap 收起 IME

第 5.2 节提到的"IME 收起优先"分支——**当前焦点在 textarea / input 时，tap 不发 SGR，改成 blur**。

结合长按 → blur tap → 长按 这个循环：

```
长按 → IME 弹（focus DirectInputCapture）
打字
短 tap → IME 收（blur）
长按 → IME 弹
...
```

为了不让 blur 跟 focus guard 打架，blur 时设 `userIntentBlurTs = performance.now()`，guard 在 300ms 内尊重不抢回。

### 6.5 iOS focus guard（焦点保活）

实测发现：长按 → focus 成功 → IME 弹起 → **50-200ms 后焦点被悄悄抢回 body** → IME 收起，用户看到"闪一下"。

抢焦点的具体来源不明（Safari 不返回 focusout 的 stack trace），可能是：
- 浏览器合成的 click 即使 preventDefault 仍触发默认 focus 转移（WebKit 已知行为）
- visualViewport resize 触发的某处副作用 blur
- React 同期重渲染（卸载 LongPressIndicator）时序问题

**修法：focus guard**——长按 focus 后启动 400ms 监听窗口，期间 textarea 被 blur 到 body 就立即 refocus：

```ts
const armedAt = performance.now();
const PROTECT_MS = 400;
const focusGuard = (fe: FocusEvent): void => {
  if (performance.now() - armedAt > PROTECT_MS) {
    document.removeEventListener('focusout', focusGuard, true);
    return;
  }
  // 用户主动 blur（短 tap 收 IME）：尊重
  if (performance.now() - userIntentBlurTs < 300) return;
  // 用户切去别的可 focus 元素：尊重
  if (related && related !== document.body) return;
  // 只保护 textarea / input
  if (t?.tagName !== 'TEXTAREA' && t?.tagName !== 'INPUT') return;
  // refocus
  requestAnimationFrame(() => {
    if (document.activeElement === document.body) {
      t.focus({ preventScroll: true });
    }
  });
};
document.addEventListener('focusout', focusGuard, true);
window.setTimeout(() => {
  document.removeEventListener('focusout', focusGuard, true);
}, PROTECT_MS + 50);
```

**三个尊重条件**：

1. **超出 400ms 窗口**：解除 guard，让正常焦点逻辑接管
2. **用户主动 blur（300ms 内）**：tap 收 IME 时设了 `userIntentBlurTs`，guard 看到不抢
3. **focus 转到非 body 元素**：用户点了 toolbar 按钮等真正可 focus 的元素，guard 尊重

这套 pattern 在 iOS 移动编辑器中常见（CodeMirror Mobile、ProseMirror touch wrapper、TipTap mobile 都用类似 trick）。

### 6.6 ConsolePage 的 helper-textarea focus 劫持

老的 `ConsolePage.tsx`（兼容路径，目前用户实际跑的是 `MultiInstanceConsole`）有个 focus 劫持逻辑：

```tsx
const handler = (e: FocusEvent): void => {
  if (!el?.classList.contains('xterm-helper-textarea')) return;
  if (isMouseReportingActive(termRef.current)) return; // ← 关键
  if (terminalTapRef.current !== null) return;
  if (performance.now() - terminalReleaseTsRef.current < 250) return;
  if (getSelection()) return;
  requestAnimationFrame(() => {
    inputBarRef.current?.focus({ preventScroll: true });
  });
};
```

**作用**：xterm 自己 focus helper-textarea 时（比如 mouse 处理副作用），自动转给 InputBar，避免用户对着不可见的 xterm textarea 输入。

**mouse-active 时跳过**：在 Claude TUI 等场景下，xterm helper-textarea 应该保持 xterm 自己控制（虽然我们 hook 也阻止了 mousedown 调它）；不要硬抢给 InputBar 然后弹 IME。

### 6.7 小结

IME 控制是本项目最复杂的部分，涉及 user gesture 同步、focus guard、用户意图区分（tap 收 / 长按弹 / 主动切别处）。最终用户体感是"长按弹键盘、点屏收键盘"两个清晰动作，背后机制相当繁琐。

## 第七章 文本选择与剪贴板

### 7.1 章节引言

终端用户常用动作：拖选一段输出文字，复制粘贴到别处。这看似简单，在 TUI 启用 mouse reporting + 我们拦了 mousedown 之后变成了一个需要专门设计的子系统。

### 7.2 PC 鼠标拖选

**问题路径**：
1. mouse-active 时 xterm 自己 disable 了 SelectionService（`Terminal.ts:547`）
2. 必须按 Shift+鼠标才能强制选择（xterm 默认设计）
3. 我们 hook 又 stopImmediatePropagation 阻止了 xterm 的 mousedown handler，连 SelectionService 的 mousedown 也阻止了

**解决**：手动调 SelectionService.handleMouseDown：

```ts
export function dispatchSelectionMouseDown(term: unknown, e: MouseEvent): boolean {
  const core = (term as any)?._core;
  const svc = core?._selectionService;
  if (!svc?.handleMouseDown) return false;
  try {
    svc.enable?.();              // 强制启用，绕过 mouse-active 的 disable
    svc.handleMouseDown(e);
    return true;
  } catch {
    return false;
  }
}
```

调用时机：onMouseDown 里 `if (!fromTouch) dispatchSelectionMouseDown(...)`。

**`enable()` 调用**：默认 mouse-active 时 SelectionService 是 disabled 状态，要求 Shift+click 才工作；我们调 `enable()` 让它进入正常路径，无需修饰键。

### 7.3 选择高亮的瞬时消失问题

**现象**：用户拖选完成松开手 → 选区高亮**立即消失**。

**原因**：xterm 内部某些路径在 mouse-active 模式下 mouseup 时会清掉选区（具体路径未深查，可能是 SelectionService 自己看到 mouse-active 后撤销）。

**应对**：不去修复"高亮停留"，改成**mouseup 时立即把选区文本写到剪贴板**——文字到剪贴板就行了，高亮停不停留无所谓：

```ts
const onMouseUp = (): void => {
  const ctx = getCtx();
  if (!ctx) return;
  const fromTouch = performance.now() - lastTouchTs < TOUCH_MEMORY_MS;
  if (fromTouch) return;       // 仅 PC，移动端不走自动复制
  const text = ctx.term.getSelection?.() ?? '';
  if (!text) return;
  void copyToClipboard(text);  // 同步在 user-gesture 链路里调
};
```

监听挂在 `document` 上而非 element：拖动可能在 element 外抬起。

### 7.4 跨上下文剪贴板封装

`utils/clipboard.ts` 的 `copyToClipboard` 提供三档降级：

| 档位 | 触发条件 | 实现 | 可靠性 |
|---|---|---|---|
| `clipboard` | secure context（HTTPS / localhost）| `navigator.clipboard.writeText` | 100% |
| `execCommand` | 桌面 / Android 非 secure | 临时 textarea + `document.execCommand('copy')` | 高（但 deprecated）|
| `selectOnly` | iOS + 非 secure | 不假装复制，引导用户长按系统拷贝 | N/A（UI 层处理）|

**关键约束：execCommand 必须在 user gesture 同步链路内调**——这就是为什么 `onMouseUp` 不能 await / rAF 后调，必须同步。

`detectCopyCapability()` 检测当前环境能用哪档：

```ts
if (navigator.clipboard?.writeText && window.isSecureContext) return 'clipboard';
if (isIOS) return 'selectOnly'; // iOS 非 secure 上 execCommand 假成功真失败
if (document.queryCommandSupported('copy')) return 'execCommand';
return 'selectOnly';
```

iOS bug：execCommand('copy') 在 iOS 上即使返回 true 也实际没复制（WebKit bug 156529 / clipboard.js #587）——本项目检测到 iOS + 非 secure 时直接回退 `selectOnly`，不浪费用户期待。

### 7.5 用 copyToClipboard 的所有调用点

统一使用同一个 helper，避免每个调用点各自实现降级：

| 文件 | 用途 |
|---|---|
| `useTouchSwipeScroll.ts` | PC 拖选完成自动复制 |
| `InstanceView.tsx` | Cmd+C / Ctrl+C 复制 xterm 选区 |
| `ConsolePage.tsx` | 同上（兼容路径）|
| `IpChangeToast.tsx` | 复制新 IP URL |
| `AboutSettings.tsx` | 复制版本号 |
| `ShareSheet.tsx` | 复制分享 URL |

### 7.6 移动端选词的现状

当前**移动端不支持自动选词复制**。原因：

- 短 tap 槽位 = SGR 点击
- 短 swipe 槽位 = SGR 滚动
- 长按槽位 = 弹 IME

可用的"剩余手势"只有双指拖动 / 三指 / 双击-保持-拖。这些都需要用户学习，UX 不直观。当前妥协：移动端用户要复制就用桌面浏览器，或者长按 InputBar 内的内容（系统原生选择菜单）。

未来如果需要，候选方案是"双指拖动 = 选词"（Termius 的做法）。

### 7.7 小结

PC 拖选 = 手动 dispatch 给 SelectionService + mouseup 同步复制；移动端选词暂不支持。剪贴板写入统一封装在 `copyToClipboard`，三档降级覆盖 HTTPS / LAN HTTP / iOS 三种环境。

## 第八章 长按交互设计

### 8.1 章节引言

长按是触摸界面里语义最明确的"我要做点别的事"信号。本项目把它独占给"弹 IME"功能，其他可能的语义（选词 / 右键菜单）暂不实现，避免槽位冲突。本章详细讲长按的全链路：识别 → 视觉反馈 → 触发 → 抑制其他副作用。

### 8.2 长按识别参数

```ts
const TAP_DIST_PX = 10;        // 位移 ≤ 10px 才算 tap / 长按候选
const TAP_TIME_MS = 500;       // 总时长 ≤ 500ms 算 tap，> 500 也可能是长按
const PROGRESS_DELAY_MS = 200; // 进度条延迟 200ms 显示
const longPressMs = 600;       // 长按触发阈值（默认）
```

**设计理由**：

- **TAP_DIST_PX 10px**：Hammer.js 默认 threshold 9，CodeMirror 6 用 10px 的 drag slop，业界共识
- **PROGRESS_DELAY_MS 200ms**：避免短按 / 快速滑动也闪一下进度条干扰用户。200ms 够区分"无意触碰"和"明显在按"
- **longPressMs 600ms**：iOS 系统长按 ~500ms，Android ~500ms，常见 web 移动应用 600ms。比系统略长是为了不与系统级长按行为冲突
- **TAP_TIME_MS 500ms**：单击的最大时长，长按从 600ms 起，500-600 之间是"模糊带"算 tap 也算长按候选都还可以

### 8.3 长按状态机

```
touchstart
  ├─ 进入 tap 候选（tapStartTs > 0）
  ├─ 启动 progressShowTimer（200ms 后显示进度条）
  └─ 启动 longPressTimer（600ms 后 longPressFired = true）

touchmove
  ├─ 位移 > 10px → cancelLongPress（清两个 timer + 关进度条 UI + tap 候选作废）
  └─ 否则继续

touchend
  ├─ cancelLongPress（清未触发的 timer）
  ├─ 如果 longPressFired → 同步调 onLongPressRef.current()，启动 focus guard
  └─ 否则进入 tap 判定（见第 5.2 节）
```

`cancelLongPress` 包含：清 longPressTimer + 清 progressShowTimer + 关进度条 UI（如果已显示就调 `onLongPressCancel`，没显示就不打扰）。

### 8.4 进度条 UI

`LongPressIndicator` 组件：

```tsx
<div
  key={`${x}-${y}`}              // key 重置 CSS animation
  className={s.root}
  style={{ left: x - 40, top: y - 36 }}  // 触摸点上方 36px、左偏 40
>
  <div className={s.bar} style={{ animationDuration: `${durationMs}ms` }} />
</div>
```

CSS：

```scss
.root {
  position: fixed;       // viewport 坐标，不受容器变换影响
  width: 80px;
  height: 3px;
  border-radius: 2px;
  background: rgba(255, 255, 255, 0.15);
  overflow: hidden;
  pointer-events: none;  // 不拦截手势
  z-index: 9999;
}
.bar {
  height: 100%;
  background: t.$accent;
  transform-origin: left center;
  animation-name: atrLongPressGrow;
  animation-timing-function: linear;
  animation-fill-mode: forwards;
}
@keyframes atrLongPressGrow {
  from { transform: scaleX(0); }
  to   { transform: scaleX(1); }
}
```

**动画时长**：`PROGRESS_BAR_DURATION_MS = LONG_PRESS_MS - PROGRESS_BAR_DELAY_MS = 600 - 200 = 400ms`。进度条出现时已经走了 200ms（不可见的"潜伏期"），剩余 400ms 内走满到长按触发。

**位置随触摸点动态**：用 `style={{ left: x - 40, top: y - 36 }}`，每次触摸都按当前坐标定位。

**key 重置**：用 `${x}-${y}` 作 React key，每次新的 touchstart 都重新挂载组件 → CSS animation 从 0 开始。如果只改 props 不改 key，CSS animation 不会重启。

### 8.5 长按触发 IME 的同步性

第 6.3 节已详述：长按定时器只标记 `longPressFired = true`，真正调 `inputBarRef.focus()` 留到 `touchend` 同步触发——iOS user gesture 要求。

如果用户**按住 600ms 后继续按着没抬手**：进度条已消失（armed 完成），IME 不弹（focus 没调）。这是预期行为——给用户"按住等弹"的视觉反馈但不强制 commit，让他可以继续犹豫"要不要真的弹"，决定就抬手。

### 8.6 长按与其他手势的冲突

**冲突 1：长按 vs swipe**
位移超 10px → `movedBeyondTap = true` → cancelLongPress → 后续完全走 swipe 路径
解决：阈值小（10px）让识别快速分流

**冲突 2：长按 vs 多指**
touchstart 时 `if (e.touches.length !== 1) { tapStartTs = 0; return }` → 多指不进入 tap / 长按候选
解决：直接放弃接管，让浏览器 / 系统处理

**冲突 3：长按 vs iOS 系统长按选词**
iOS 系统在 `touchstart` 后 ~500ms 会自己尝试弹"选择菜单"。我们的长按是 600ms，又只在 mouse-active 时启动 → 普通 shell 长按系统选择正常工作；TUI 内长按 = 我们接管 → 系统选择被覆盖
解决：仅 mouse-active 时启用进度条 + 长按判定（在 touchstart 启动 timer 时检查 `getCtx()`），普通 shell 完全放给系统

**冲突 4：长按触发后的合成 click**
浏览器在 touchend 后会合成 click。我们 hook 在 fromTouch 时 stopImmediatePropagation 拦下，避免它冒泡到 InstanceView 容器 onClick 重复 focus
解决：见第 5.5 节

### 8.7 小结

长按只服务一件事——弹 IME。通过 200ms 延迟显示进度条 + 600ms armed + touchend 同步触发的三段式状态机，把"按住"这个手势从模糊变成有清晰反馈、有 user gesture 资格的精确动作。

## 第九章 跨平台冲突一览

### 9.1 章节引言

前面各章按"功能"组织，本章按"平台 × 配置"组织，列出每种组合的预期行为，便于回归测试和未来回顾。

### 9.2 桌面浏览器 × 普通 shell（mouse reporting 未激活）

| 操作 | 结果 |
|---|---|
| 鼠标点击 xterm | 容器 onClick → focus InputBar / DirectInputCapture |
| 鼠标拖动 | xterm SelectionService 选中文本 |
| 双击 | xterm SelectionService 选词 |
| 鼠标滚轮 | xterm 自带 scrollback 滚动 |
| 键盘输入 | InputBar / DirectInputCapture 接收 |

hook 的 `getCtx()` 因 `isMouseReportingActive` 返回 false 而返回 null → 完全不接管。

### 9.3 桌面浏览器 × Claude TUI（mouse reporting 激活）

| 操作 | 结果 |
|---|---|
| 鼠标单击菜单 | hook mousedown → 拼 SGR press+release → TUI 响应 |
| 鼠标拖选 | hook mousedown → SGR + dispatchSelectionMouseDown → 选中（高亮可能瞬时消失但 mouseup 时已复制到剪贴板）|
| 双击 | xterm SelectionService（mousedown 已被喂）识别多次 click 选词 |
| 鼠标滚轮 | hook wheel → 拼 N 行 SGR wheel byte（N = scrollLines）→ TUI 滚 N 行 |
| Cmd+C | 复制 xterm 选区到剪贴板 |
| 键盘输入 | DirectInputCapture（如果 useInputBar=false）/ InputBar |

### 9.4 移动端 × 普通 shell（mouse reporting 未激活）

| 操作 | 结果 |
|---|---|
| 短 tap | 容器 onClick → focus InputBar → 弹 IME |
| 长按 | iOS 系统长按选词菜单（hook 不接管）|
| 单指垂直滑动 | xterm 自带 scrollback（hook 不接管）|
| 单指横向滑动 | 系统横向选择 / 翻页 |
| 多指 | 系统手势（缩放 / 滚动）|

### 9.5 移动端 × Claude TUI（mouse reporting 激活）

| 操作 | 结果 |
|---|---|
| 短 tap（IME 未弹）| hook touchend → 拼 SGR → TUI 响应点击 |
| **短 tap（IME 已弹）** | hook touchend → blur 当前 textarea → IME 收起，不发 SGR |
| 长按 600ms 抬手 | 进度条满 → focus InputBar → IME 弹起（带 400ms focus guard 防被抢）|
| 长按 600ms 不抬手 | 进度条满消失（armed），IME 暂不弹，等抬手 |
| 单指垂直滑动 | hook → SGR wheel byte × scrollLines 行 → TUI 滚 |
| 单指横向滑动 | hook 看到 vertical=false → active=false 放过 → xterm / 系统选择 |
| 多指 | hook 不接管 |

### 9.6 ControlsSection 各设置项关闭后的影响

| 设置 | 关掉后影响 |
|---|---|
| `tuiScrollEnabled = false` | hook effect 直接 return，所有 wheel / touch / click 都给 xterm 自己处理。普通 shell 一样，TUI 内回到"xterm 自带行为"——可能崩或不响应 |
| `tuiTapEnabled = false` | 触摸 tap 不发 SGR；wheel / 长按 / mousedown 仍按原逻辑工作 |
| `useInputBar = false` | 切到 DirectInputCapture，键盘输入实时发；中文 IME 兼容性下降 |
| `scrollLines` 调整 | 仅影响每次"滚动事件"的 SGR wheel 字节数量，scrollLines × 1 个 byte / step |

### 9.7 小结

平台 × 配置矩阵把所有交互的预期行为定型。任何修改 hook 都应该跑一遍这个矩阵确认没有回归。

## 第十章 已实现的操作总清单

### 10.1 章节引言

按用户视角列出每个具体操作 + 操作描述 + 触发条件 + 实现细节。这是回归测试 / 用户文档的真相源。

### 10.2 桌面端操作

#### 10.2.1 单击 TUI 按钮 / 链接

- **触发**：mouse reporting 激活时鼠标左键单击 xterm 区域
- **行为**：发送 SGR `\x1b[<0;col;rowM\x1b[<0;col;rowm` 给 TUI，col/row 由 `clientToCell` 按鼠标位置精确换算
- **实现**：`useTouchSwipeScroll.ts` 的 `onMouseDown` capture 阶段拦截 + 自己拼字节，绕开 xterm v5 的 `getMouseReportCoords` 崩溃路径

#### 10.2.2 鼠标拖选文本

- **触发**：鼠标按下后拖动到目标位置抬起
- **行为**：选中区域文本，松开瞬间自动写入剪贴板
- **实现**：mousedown 喂给 `dispatchSelectionMouseDown` 启动 SelectionService（先调 `enable()` 绕过 mouse-active disable），mouseup 同步在 user gesture 链路里调 `copyToClipboard(term.getSelection())`
- **已知问题**：选区高亮在松开瞬间可能消失，但文本已经写入剪贴板

#### 10.2.3 双击选词

- **触发**：在 xterm 区域快速双击
- **行为**：xterm SelectionService 识别多次 click → 自动选中整词
- **实现**：xterm 内置；mousedown 已经被我们喂给 SelectionService，多次 mousedown 让它判定双击

#### 10.2.4 鼠标滚轮滚动 transcript

- **触发**：mouse reporting 激活时滚一格鼠标轮
- **行为**：发送 N 个 SGR wheel byte（N = scrollLines），TUI 内部滚 N 行；上滚 button=64，下滚 button=65
- **实现**：`onWheel` capture 阶段拦截 + 拼字节；`scrollLines='half'/'full'` 时按 `term.rows` 实时计算

#### 10.2.5 Cmd+C / Ctrl+C 复制选区

- **触发**：xterm 内有选区时按 Cmd+C / Ctrl+C
- **行为**：复制选区文本到剪贴板
- **实现**：`InstanceView.tsx` keydown handler，调 `copyToClipboard`

#### 10.2.6 键盘输入

- **触发**：用户在键盘上敲字
- **行为**：InputBar 模式 → 文字进 InputBar 缓冲，回车发送；DirectInputCapture 模式 → 每个按键实时发往 PTY
- **实现**：取决于 `useInputBar` 设置；hook 不直接处理 keyboard，由两个 textarea 自己接收

### 10.3 移动端操作

#### 10.3.1 触摸 tap = 点击 TUI 按钮

- **触发**：单指 tap，位移 ≤ 10px、时长 ≤ 500ms、无长按 armed、当前焦点不在 textarea
- **行为**：发送 SGR `\x1b[<0;col;rowM\x1b[<0;col;rowm`，col/row 用 `changedTouches[0]` 精确换算
- **实现**：`onTouchEnd` 同步判定 + 发字节

#### 10.3.2 触摸 tap = 收起 IME

- **触发**：单指 tap 时**当前焦点已在 textarea / input**（说明 IME 已弹）
- **行为**：blur 当前焦点 → IME 收起，**不发 SGR**
- **实现**：`onTouchEnd` 在 isTap 分支前先检查 `document.activeElement?.tagName`；blur 同时设 `userIntentBlurTs` 让 focus guard 不抢回

#### 10.3.3 单指滑动 = 滚动 TUI

- **触发**：单指垂直滑动（ady > adx × 1.5）
- **行为**：每滑过 80px = 一次"滚动事件"= 发 scrollLines 行 SGR wheel byte；下滑发 button=64（看上面），上滑发 button=65（看下面）
- **实现**：`onTouchMove` rAF 合批 + `flushSwipe` 计算 baseSteps × linesPerStep

#### 10.3.4 单指横向滑动 = 让位给系统

- **触发**：单指横向滑动（ady ≤ adx × 1.5）
- **行为**：hook 设 `active = false`，touchmove 不再处理，让 xterm 或系统接管（横向选择 / 翻页）
- **实现**：`onTouchMove` 方向判定分支

#### 10.3.5 长按 600ms 弹 IME

- **触发**：单指按住 ≥ 600ms 不动（位移 ≤ 10px），mouse reporting 激活，抬起手
- **行为**：进度条 200ms 后出现 → 400ms 后走满 → armed → 抬手时 focus InputBar / DirectInputCapture → IME 弹起
- **实现**：双 setTimeout（progressShowTimer + longPressTimer）+ touchend 同步调 onLongPress + 400ms focus guard 防焦点被抢

#### 10.3.6 多指手势

- **触发**：≥ 2 指
- **行为**：hook 不接管，浏览器 / 系统处理（pinch zoom 等）
- **实现**：`if (e.touches.length !== 1) return`

### 10.4 跨平台操作（设置面板）

#### 10.4.1 切换输入方式

- **触发**：设置 → 操作 → 输入方式 → 选"底部输入框"或"直接输入"
- **行为**：切换 useInputBar 字段，立即重渲染对应 textarea，不需要刷新
- **实现**：`ControlsSection.tsx` 调 `setInput({ useInputBar: ... })`

#### 10.4.2 开关 TUI 滚动接管

- **触发**：设置 → 操作 → TUI 滚动接管 → 开启 / 关闭
- **行为**：useEffect deps 包含 `enabled`，关闭时 cleanup 卸载所有 listener；重新打开时重挂
- **实现**：useTouchSwipeScroll opts.enabled

#### 10.4.3 开关 TUI 触摸点击

- **触发**：设置 → 操作 → TUI 触摸点击 → 开启 / 关闭
- **行为**：关闭时 tap 不发 SGR；wheel / 长按 / mousedown 仍按原逻辑工作（仅"tap → click"这一条路径 disable）
- **实现**：`tuiTapEnabledRef.current` 在 onTouchEnd isTap 分支检查

#### 10.4.4 调整每次滚动行数

- **触发**：设置 → 操作 → 每次滚动行数 → 选 1 行 / 3 行 / 5 行 / 10 行 / 半屏 / 一屏
- **行为**：所有后续滚动事件按新行数计算
- **实现**：`scrollLinesRef.current` 在 `flushSwipe` / `onWheel` 实时读取，无需重挂 listener

### 10.5 小结

共计 16 个明确的用户可见操作，覆盖单击 / 拖选 / 双击 / 滚动 / 复制 / 长按 / 设置 7 个交互类别。每个操作都有明确的触发条件、行为定义、实现位置——这是后续维护和扩展的基线。

### 11.7 数据流 / 时序总览

```
用户触摸 / 鼠标
    │
    ↓ 浏览器 DOM 事件
    │
[useTouchSwipeScroll capture]
    │
    ├─ 满足 mouse-active + alt-screen → 拦下
    ├─ 拼 SGR byte
    └─ 通过 onSendKey 回调
        │
        ↓
    [InstanceView]
        send({type:'user_input', data: sgrBytes})
        │
        ↓ WebSocket
    [backend]
        pty.write(sgrBytes)
        │
        ↓ PTY
    [Claude TUI / vim / htop]
        识别 SGR → 内部状态变化 → 输出 ANSI 重绘
        │
        ↓ PTY → WebSocket
    [前端 useTerminal]
        term.write(bytes) → xterm 渲染
```

整个链路在 50-200ms 内完成。

### 11.8 关键设计原则

1. **xterm 仅做渲染**：所有输入接管都绕开 xterm 的 input 路径，xterm 只负责 `term.write()` 字节渲染
2. **配置实时生效**：hook 的所有可变参数都通过 ref 读，不进 effect deps；除了主 `enabled` 开关其他改动都不重挂 listener
3. **fromTouch 标志区分输入源**：`lastTouchTs` 时间戳 800ms 窗口判触摸 vs 真鼠标
4. **iOS focus guard**：所有 IME 触发后启动 400ms focusout 监听窗口，被悄悄抢焦点立即抢回
5. **userIntentBlurTs 标志**：用户主动 blur 时设时间戳，guard 在 300ms 内尊重不抢回
6. **同步在 user gesture 链路调 focus / copy**：iOS / 非 secure context 的硬性要求
7. **私有 API 集中封装**：`xterm-internals.ts` / `clipboard.ts` 集中所有"hack" 调用，未来 xterm 升级 / 浏览器变化时改一处
8. **设置项保守开放**：默认值都打开（tuiScrollEnabled / tuiTapEnabled），但提供关闭开关给"我就要原始 xterm 行为"的用户

### 11.9 小结

技术细节清单是排错时的查表索引。每次 xterm 升级、iOS 大版本更新、新加交互手势时，都先回头看这张表，对齐每一项的当前状态。

## 总结

本项目把"在 web 浏览器里开 TUI"这件事从一个 xterm.js 默认配置的 demo，做到了一个真正可以日常用的移动端 + 桌面端混合产品。核心工作量集中在三件事：

1. **统一鼠标 / 触摸的输入语义**：用 SGR 1006 mouse byte 作为唯一中介，前端拦截所有原始事件按用户意图重写
2. **iOS Safari 适配**：user gesture 同步链路、focus guard、IME 弹起 / 收起、execCommand fallback、QuickType 防御
3. **配置 + 默认值的克制设计**：4 个设置项 + 3 个默认值都打开，普通用户开箱即用，高级用户可以关闭回到 xterm 原生行为

后续可能的扩展方向：

- 移动端选词（双指拖动 / 长按延伸 / 等待 xterm 7.0 PR #5685）
- 桌面 PWA 集成（无浏览器边框）下的剪贴板权限
- 更精细的 mouse mode 区分（仅 button-event 的 TUI 不发 wheel byte 等）
- 国际化键盘布局对 IME 长按 timing 的影响（韩语 / 日语 IME 与中文不同）
